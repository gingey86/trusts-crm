# Conceptual relational schema

Authoritative narrative lives in ../docs/architecture/data-model.md and ADRs. This is the mapping contract for Prisma/SQL, not an applied migration. Implement two schema/client/migration trees: prisma/control and prisma/tenant.

## Control relations

Auth models are generated by the installed Better Auth adapter/plugin. User 1:N Membership N:1 TenantRegistry. Membership unique(userId,tenantId). Registry slug unique; enabled only after provisioning health checks. PlatformSecurityEvent holds operational IDs/redacted actions, never CRM payloads. connectionSecretRef references private config, not client-visible URL.

## Tenant relations

Organisation is singleton; FinancialYear belongs to it. The initial internal FX-history representation is BudgetFxRateRevision → FinancialYear, unique(year,source,target,revision); rate >0. Users edit annual rates without managing those identifiers. Financial-year ranges use [start,endExclusive), cannot overlap. Currency must be a supported ISO code. ActorReference has a stable tenant ID and optional mapping to a current control identity, with no cross-database foreign key. Author, owner and responsible-user fields reference the stable actor ID, so restoring data with fresh authentication accounts preserves historical attribution.

Funder 1:N Opportunity; Opportunity 1:N Application (only one pending, v0.1 reapplications use new Opportunities). Successful Application 0:1 Grant, unique applicationId; Grant 1:N Obligation. Grant funder derives from linked Application/Opportunity, with consistency validation if denormalised for queries.

Contact 1:N ContactFunderAffiliation N:1 Funder, dated history, one open/current affiliation. OpportunityContact and GrantContact joins are unique pairs. Interaction belongs to Funder, optionally Opportunity or Grant; InteractionContact references Contact and affiliation snapshot so changing a job does not rewrite history.

Task has at most one typed parent FK among Funder, Contact, Opportunity, Application, Grant, Obligation; parentless ordinary Task permitted. Use a SQL CHECK on parent count. NextAction designates exactly one Funder or Opportunity and one linked open Task; unique funderId/opportunityId/taskId with CHECK exactly one parent. Completing, cancelling or archiving the Task clears designation transactionally.

Document owns metadata/opaque storage key; DocumentLink has exactly one typed parent FK among Funder, Contact, Opportunity, Application, Grant, Obligation, Task, Interaction. SQL CHECK parent count =1 and per-parent pair uniqueness. Document may have several links; no arbitrary unvalidated recordType/recordId relation. Bytes never enter rows. Grant can link to submitted Application documents directly.

## Types and constraints

Initial SQL mapping: UUID IDs; numeric(20,4) amounts, numeric(20,10) rates, numeric(5,4) probability. These precisions implement the exact-decimal constraint and must be validated against supported bounds during implementation. Decimal strings in wire/fixtures. amount>=0; probability 0–1; null amount/probability distinct from zero. Amount requires currency; optional payment amount also requires planning year. Typical min<=max. Application Successful requires award/currency and actual decision date; terminal decisions require date. Grant period start<=end where both set; grant completion checks unresolved obligations in service.

Date-only @db.Date fields for due/deadline/submitted/decision/grant/interaction/FY; timestamptz for audit/created/updated/archived/auth. No writable converted values/calendar-event rows. Application owns dates after submission; source-field projection prevents duplicate events.

Foreign keys RESTRICT hard deletion. Ordinary archival preserves IDs/joins. Add version integer for optimistic updates, with server actor attribution. Audit tables deny runtime UPDATE/DELETE. Multi-record workflow + audit uses one tenant transaction. Grant conversion unique(applicationId) and idempotency; import content/idempotency keys prevent accidental repeat confirmation.

No canonical domain, document, settings, financial-year/FX, archive-metadata or business-audit table has age-based TTL, purge or automatic archival. Support at least a seven-year audit horizon and longer organisation-controlled retention. Clearing a current NextAction designation retains its significant history in business audit. Technical staging/package/cache cleanup and infrastructure log/backup rotation are separate policies; deliberate erasure is a controlled authorised procedure.

## Indexes

Index active list/filter paths: Funder(status,owner), Opportunity(stage,owner,planningYear), deadline/next-action Task due/status, Application(decisionStatus,expectedDecisionDate/submittedDate), Grant(status,endDate), Obligation(status,dueDate), Interaction(funderId,occurredDate), DocumentLink parent FKs and AuditEvent(timestamp,target). Include archived predicates where useful after measurement. Paginate search; add PostgreSQL text indexes only after verifying query plans. No global index spanning tenant CRM.

## Export compatibility

Lossless JSON preserves IDs, relationships, nulls, decimal strings, date strings, archive state, rates and actor references. Export includes a tenant-scoped membership roster and relevant membership security events without credentials or other tenants' records. Restore preserves the organisation UUID, rejects collisions with existing tenants and creates fresh authentication accounts and memberships before activation. The hosted and self-hosted schemas remain identical. Fixture aliases map deterministically to UUIDs; unknown aliases fail validation.
